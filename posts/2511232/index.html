This article introduces the core workflow and technical key points of QEMU hardware modeling. It first outlines the six stages of QEMU virtual machine creation: command-line parsing, Machine type selection and registration, object instantiation, hardware device initialization, accelerator and CPU initialization, and virtual machine startup, covering key components such as the Main function, MachineClass, MachineState, and QOM. Subsequently, using the PL011 UART and edu educational devices as examples, it provides a detailed analysis of peripheral modeling implementation methods, including device type definition, state structure design, class initialization, MMIO mapping, FIFO management, interrupt generation, DMA transfer, and background thread asynchronous processing. The article also thoroughly explores the complete interrupt modeling workflow, from device-level triggering and PLIC arbitration to CPU interrupt injection and Guest OS handling, and mentions debugging and tracing methods. Overall, this article systematically demonstrates how QEMU precisely simulates hardware behavior through the QOM object model, providing support for full-stack development from bare-metal programs to the Linux kernel.

Machine Modeling

The core process of QEMU creating a virtual machine can be divided into 6 stages, each involving specific components and operations

Command Line Parsing

Entry function: main() Key operations:

  • Parse the -M parameter to specify the machine type (e.g., virt)
  • Initialize the QOM (QEMU Object Model) type system
  • Create the global state machine MachineState

system/main.c

system/vl.c

Machine Type Selection and Registration

Core component: MachineClass (machine class description)

Key operations:

  • Match the user-specified machine type via select_machine()
  • Look up the corresponding TypeImpl from the global type table type_table

Machine Object Instantiation

Core component: MachineState (machine runtime state)

Key operations:

  • Via QOM’s object_new_with_class() to instantiate the machine
  • Initialize basic properties such as memory and CPU topology

Hardware device initialization

Core phase: machine_run_board_init()

Key operations:

  • Call the machine-specific init() method (e.g., virt for RISC-V virt_machine_init()）
  • Initialize core components such as CPU, memory controller, and bus

Accelerator and CPU initialization

Core components: AccelState and CPUState

Key operations:

  • Select KVM/TCG accelerator based on -accel parameter
  • Create vCPU thread and bind to physical CPU

Start virtual machine

Final phase: qemu_main_loop()

system/runstate.c

Peripheral Modeling (PL011 UART)

The modeling of the PL011 UART in QEMU fully demonstrates the core process of hardware peripheral emulation:

  • Type system integration: Implementing device class inheritance through QOM
  • Precise state modeling: Full lifecycle management of registers, FIFO, and interrupt states
  • Hardware interface implementation: MMIO callbacks handle CPU access, character backend interfaces with host I/O
  • Interrupt system integration: Working in coordination with the Platform-Level Interrupt Controller (PLIC)
  • Device lifecycle: Implementing a complete lifecycle including reset, migration, and destruction

Device type definition

Core mechanism: QEMU Object Model (QOM)

Key operations:

  • Define TypeInfo structure to describe device type
  • Implement class initialization (class_init) and instance initialization (instance_init)
  • Register to the global type system

Device state structure design

Core component: PL011State

Key fields:

  • Register state (lcr, imsc, etc.)
  • FIFO buffer
  • Interrupt signal line
  • Character backend (CharBackend)

Device class initialization

Core tasks:

  • Set device properties

  • Bind realize and reset methods

  • Define device migration support

Device instantiation and hardware connection

Core operations:

  • Initialize memory region (MemoryRegion)
  • Register MMIO callback functions
  • Connect interrupt signal
  • Bind character device backend

Precise register modeling:

  • Implement precise behavior for all 32 registers
  • Handle special bits (e.g., FIFO enable bit, interrupt mask bit)
  • Support baud rate calculation (IBRD/FBRD)

FIFO state machine:

Clock domain handling:

  • Implement pl011_clock_update callback
  • Handle baud rate change events
  • Support dynamic clock adjustment

Migration support:

Performance optimization:

  • Use bitwise operations instead of division to calculate baud rate
  • FIFO operations use masks instead of modulo operations
  • Interrupt state caching reduces computation count

This modeling approach allows PL011 to accurately simulate real hardware behavior in QEMU, supporting full-stack development from bare-metal programs to the Linux kernel.

Peripheral modeling (edu device)

In computer systems, the essence of CPU-peripheral interaction is address access and interrupt notification:

  • Address Access: CPU reads/writes device registers via MMIO (Memory-Mapped I/O) or PIO (Port I/O)
  • Interrupt Notification: Peripherals send event signals to the CPU via the interrupt controller

  3. Calculate factorial
  4. Handle interrupt: clear status flags in interrupt service routine

Key points summary

edu encapsulates the 5 core elements of peripheral modeling:

Mainly involves:

  • State machine model: represent device state through register bits (e.g., computing/completed)
  • Asynchronous processing: time-consuming operations are handed off to background threads to avoid blocking the vCPU
  • Address isolation: each device has independent MMIO space
  • Interrupt abstraction: supports both traditional INTx and modern MSI modes
  • DMA safety: address validation prevents VM escape

Interrupt modeling

  • Device layer: PL011 triggers interrupt signals based on hardware status
  • Interrupt controller layer: PLIC implements priority arbitration and interrupt distribution
  • CPU layer: RISC-V architecture responds to external interrupts and switches context
  • Guest layer: the interrupt handler of the guest program or operating system completes the device service
