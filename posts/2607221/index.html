Supplement VRing structure (three major areas of split ring), data transfer flow, notification suppression mechanism, Packed Virtqueue, virtqueue implementation in Linux kernel and OpenAMP, and examples of Linux kernel using VRing (virtio-rng, virtio-blk)

This article introduces the basic concepts and core architecture of VirtIO (Virtual Input/Output). VirtIO is an abstraction layer between virtual machines and host devices, achieving data transmission through minimal VirtIO devices, offloading most hardware processing work to the host, thereby improving efficiency. The article elaborates on three key components of the VirtIO architecture: the front-end driver (kernel modules in the Guest kernel), the back-end device (such as VirtIO devices in QEMU), and VirtQueues/VRings. Among them, VRing is the actual data structure, with the classic layout being the split ring, consisting of three contiguous memory areas: the descriptor table, the available ring, and the used ring, utilizing a lock-free SPSC mechanism to achieve data sharing and notification between the driver and the device. The article also mentions the standardization significance of the VirtIO specification, as well as the flexibility in different implementations (such as the Linux kernel and OpenAMP).

VirtIO introduction

VirtIO, or Virtual Input/Output, is an abstraction layer for virtual machines on a host device. Essentially, it is an interface thatallows virtual machines to use the host’s devices through minimalist virtual devices (called VirtIO devices). These VirtIO devices are very minimalist because they only implement the basic requirements for sending and receiving data.

This is because in VirtIO, we let the host take care of most of the setup, maintenance, and processing of its actual hardware devices.The role of VirtIO devices is basically to transfer data to the host’s actual physical hardware。

  1. VM: I want to go to google.com. Hey virtio-net, can you tell the host to fetch this webpage for me?
  2. Virtio-net: Sure. Host, can you fetch this webpage for us?
  3. Host: Sure. I am currently fetching the webpage data.
  4. Host: Here is the requested webpage data
  5. Virtio-net: Thanks. Hey, VM, here is the webpage you requested

Although this is an overly simplified example, it still illustrates the core idea. That is, let the host’s hardware do as much work as possible, and let VirtIO handle sending and receiving data. Offloading most of the work to the host makes execution on the virtual machine faster and more efficient than emulated devices.

Another important aspect of VirtIO is that its core framework has been standardized as the official VirtIO specification. The VirtIO specification defines the standard requirements that VirtIO devices and drivers must meet (e.g., feature bits, status, configuration, general operations, etc.). This is important because it means that regardless of the environment or operating system using VirtIO, the core framework of its implementation must be the same.

While VirtIO implementations have a certain level of compliance, there is also some flexibility in their organization and setup. For example, the structure in the Linux kernelvirtqueuestructure is different from QEMU’sVirtQueuestructure.

VirtIO architecture

The architecture of VirtIO consists of three key parts:

  • Frontend driver
  • Backend device
  • VirtQueues and VRings

The figure below shows the location of each component in a typical VirtIO host and guest configuration (without vHost, SR-IOV, etc.).

The frontend VirtIO driver resides in the Guest kernel, and the backend VirtIO device resides in the virtual machine (QEMU),and the communication between them is handled in the data plane through VirtQueue and VRing。

We can also see notifications issued from the VirtIO driver and device (such as VMExit, vCPU IRQ), which are routed to KVM interrupts.

VirtIO Driver (Front-End)

In a typical VirtIO Host and Guest configuration, the VirtIO driver resides in the Guest kernel. In the Guest operating system, each VirtIO driver is treated as a kernel module. The core responsibilities of the VirtIO driver include:

  • Accepting input/output requests from user processes

  • Transmitting these I/O requests to the corresponding backend VirtIO device

  • Retrieve completed requests from the VirtIO device counterpart

For example:

  1. The I/O request for virtio-scsi might be a user wanting to retrieve a document from storage.

  2. The virtio-scsi driver accepts the request to fetch the document and sends the request to the virtio-scsi device (backend).

  3. After the VirtIO device completes the request, the document is provided to the VirtIO driver. The VirtIO driver retrieves the document and makes it available to the user.

VirtIO Device (Back-End)

Furthermore, in a typical Host and Guest configuration, VirtIO devices exist within the virtual machine. In the figure above, we will use QEMU as our (Type 2) virtual machine. This means our VirtIO device will exist within the QEMU process. The core responsibilities of the VirtIO device include:

  • Accepting I/O requests from the corresponding frontend VirtIO driver
  • Processing requests by offloading I/O operations to the host’s physical hardware
  • Making the data of the processed request available to the VirtIO driver

Returning to the virtio-scsi example:

  1. The virtio-scsi driver notifies its device counterpart that the device needs to fetch the requested document from storage on the actual physical hardware.
  2. The virtio-scsi device accepts the request and makes the necessary calls to fetch the data from the physical hardware.
  3. Finally, the device makes the data available to the driver by placing the retrieved data into the shared VirtQueue.

VirtQueues

The final key component of the VirtIO architecture is the VirtQueue, which are data structures that help the device and driver perform various I/O operations.

VirtQueues are shared in Guest physical memory, meaning each VirtIO driver and device pair accesses the same page in RAM. In other words, the VirtQueue of the driver and the device are nottwo separate synchronized regions.

There are many inconsistencies in online descriptions of VirtQueues. Some use them synonymously with virtual rings (VRings, or Virtio-rings), while others describe them separately. This is because VRings are the main feature of VirtQueues; a VRing is the actual data structure that facilitates data transfer between the VirtIO device and driver. We will describe them separately here because a VirtQueue is more than just a VRing.

Descriptor Table

The descriptor table is an array, where each element describes a data buffer:

flagsdefines three flags:

  • An I/O request often consists of multiple non-contiguous memory segments (scatter-gather). The driver fills each segment into a descriptor and usesNEXTflags to chain them intodescriptor chains；WRITEThe flags determine whether each segment is a device read (out, e.g., data for sending packets) or a device write (in, e.g., buffer for receiving packets); directions cannot be mixed on the same chain.
  • INDIRECTis a performance optimization: the driver can allocate an “indirect descriptor table” containing only a single chain, which occupies only one descriptor slot in the main table, preventing long chains from filling up the main table.

Both rings arelock-free SPSC (Single Producer - Single Consumer) ring queues: each side only writes to the ring it produces (idxmonotonically increasing, wrapping around), and only reads the ring produced by the other side, thus requiring no synchronization primitives, relying only on memory barriers to ensure visibility. This is the key design for VirtQueue’s high throughput.

Notification suppression

Notification (VMExit / inter-core interrupt) is the most expensive operation in the entire flow, so the specification provides suppression switches in two directions, set by thereceiversetting the bit,senderchecking before notifying:

  • VRING_USED_F_NO_NOTIFY(flags on the avail ring, written by the device for the driver to read): When the device sets the bit, it means “don’t keep kicking me, I will poll myself”. The driver checks this flag in thevirtqueue_kick()to decide whether to actually send the notification.
  • VRING_AVAIL_F_NO_INTERRUPT(flags on the used ring, written by the driver for the device to read): When the driver sets the bit, it means “no need to interrupt me immediately after processing”.
  • Event Idx（VIRTIO_F_EVENT_IDXfeature): Instead of using a binary switch, both parties useused_event/avail_eventto precisely inform “don’t notify me until idx reaches X”, making the suppression granularity at the buffer level.

Packed Virtqueue

VirtIO 1.1 introduced packed ring, aiming to reduce cache line usage and eliminate the multiple memory accesses caused by the separation of avail/used rings and the descriptor table in the split ring:

  • The descriptor table and the avail/used ringsare merged into a single circular descriptor array, where the descriptors themselves carry the available/used flags;
  • Each descriptor usesVRING_DESC_F_AVAILandVRING_DESC_F_USEDtwo flags’togglingto indicate state changes (distinguished by equality/inequality, combined with wrap counter wrapping), where the driver and the device each only write the flags they own;
  • The number of descriptors can be less than the queue depth, allowing the driver to publish them incrementally one by one without needing to construct a complete chain all at once.

The device and driver negotiate feature bitsVIRTIO_F_RING_PACKEDto decide whether to use the packed or split layout; the two are functionally equivalent. The Linux kernel’svirtio_ring.cimplements both sets of (vring_create_virtqueue_split()/vring_create_virtqueue_packed()), while the OpenAMP library currently only implements the split ring.

virtqueue in OpenAMP

In the OpenAMP scenario of this series (STM32MP157, A7 running Linux, M4 bare-metal firmware), the M4 side is managed by the OpenAMP library（lib/virtio/virtqueue.c) implement the same set of split ring protocols, with the division of work on both sides as follows:

  • VRing’s memory sourceThe position and size of vring are determined by M4 firmware.Resource tablein (resource table)struct fw_rsc_vdev_vringDescription (num、align、daetc.), after the A7 side remoteproc parses the resource table, it allocates the actual memory in the shared memory (carveout) and establishes the mapping based on the same vring ID. This ensures the A7’svirtio_ring.cWhat is seen with M4’s OpenAMP isthe same ring on the same physical memory。
  • data path: The send and receive buffers of RPMsg themselves are placed in shared memory, and mutually ‘handed over’ through the descriptors of vring, the specific call flow is in Virtio Rpmsg Bus Detailed analysis.
  • notification channel: OpenAMP’svirtqueue_kick()Eventually reaches the notify callback of the virtio device, which on the STM32MP157 means writing a channel flag to the IPCC to trigger a remote interrupt (see IPCC）。

Why can communication still happen even if the structures on both sides are different?

OpenAMP and Linux Kernelstruct virtqueueThe definitions are not the same (which also confirms what was said at the beginning: the specification only constrains the vring protocol and behavior, not the organization of software data structures), but as long as both parties comply with the same version of the virtio specification (with feature negotiation in agreement), the interaction on the vring is compatible.
